# Roswaal

Visual scripting for Roblox Luau and Lune Luau. Graphs live on disk as
`.nodescript` files and compile to plain `.luau` that Rojo syncs like any other
source file.

Roswaal is licensed **0BSD**: use it, modify it, ship it, train on it, no
attribution required.

## Status

Prototype. The compiler and its test suite are the load-bearing parts; the
editor is being built on top of them.

## How it fits together

Roswaal does not run inside Roblox Studio. Studio plugins have no filesystem
access, and the whole design here is file-first — so Roswaal is an external
editor that writes `.luau` into your existing source tree and lets **Rojo** do
the syncing it already does well.

```
.roswaal/scripts/*.nodescript   ->   roswaal compile   ->   src/*.luau   ->   rojo   ->   Studio
```

## The graph model

Two kinds of wire, as in Unreal's Blueprints:

- **Execution** wires define statement order. Red nodes start or end a flow.
- **Data** wires define expressions and are typed.

Nodes are **pure** (no exec pins, inlined at the use site) or **impure** (emits
a statement). Two rules do most of the work in the emitter:

1. A pure value with one consumer is spliced into its use site. With two or
   more it is bound to a local, so the expression is evaluated exactly once no
   matter how many wires leave the pin.
2. Bindings are scoped to the block that produced them. Reading a loop variable
   from outside its loop is reported as a diagnostic rather than silently
   emitting code that does not compile.

## Generated output

Every generated file carries a header:

```lua
--!strict
-- Generated by Roswaal. Do not edit this file directly;
-- edit Greeter.nodescript and recompile instead.
-- roswaal-graph: 0f3c...
-- roswaal-source: 49a09562bbba00b0
-- roswaal-output: 00dc083f917c23c2
```

`roswaal-source` hashes the *semantics* of the graph — node positions are
deliberately excluded, so tidying up a layout never shows as a diff in compiled
files. `roswaal-output` hashes the emitted body, which is how Roswaal notices
that a generated file was hand-edited and warns instead of overwriting it.

Compilation also produces a line-to-node source map, so a runtime error at
line 42 can be traced back to the node that emitted it.

## Custom nodes

Node packs are `.nodedef.json` files — data only. A pack declares pins and a
`compilesTo` template:

```json
{
  "id": "mypack.knockback",
  "title": "Apply Knockback",
  "category": "Combat",
  "inputs": [
    { "id": "in", "kind": "exec" },
    { "id": "character", "name": "Character", "kind": "data", "type": "Instance" },
    { "id": "force", "name": "Force", "kind": "data", "type": "Vector3" }
  ],
  "outputs": [{ "id": "then", "kind": "exec" }],
  "compilesTo": {
    "kind": "statement",
    "template": "$in.character.HumanoidRootPart:ApplyImpulse($in.force)"
  }
}
```

Three template kinds are available:

| kind | shape | emits |
| --- | --- | --- |
| `expr` | pure, no exec pins | an expression per output pin |
| `call` | impure, one value | `local x = <template>` |
| `statement` | impure, any outputs | the template as statements |

Placeholders: `$in.<pin>` for a resolved input expression, `$out.<pin>` for the
local an output was bound to, and the modifiers `$in.<pin>!ident` and
`$in.<pin>!raw` for text that becomes part of the generated code rather than a
runtime value.

Packs cannot use the fourth kind, `builtin`. That is reserved for the flow
nodes that open blocks, and keeping it closed means loading a third-party node
pack never executes third-party code.
